1. What it does

The SEO Planner reads your keyword rankings from Advanced Web Ranking (AWR), works out which keywords need attention and why, and builds the cheapest to-do list that deals with all of them. Every suggestion can be traced back to the ranking data that caused it.

📥ReadPositions for one keyword group, for your website and your competitors, on two dates.
🧾RepresentThe numbers become logic facts, e.g. Ranking(K, 14).
🧠Reason33 rules derive labels: dropped, striking distance, needs work, priority…
🧭PlanA search algorithm finds the cheapest sequence of SEO actions.

The result is shown as quest cards, a timeline, or a checklist. You can also ask the knowledge base your own questions and see a proof for each answer.

2. Using the app

  1. Connect. Paste your AWR API key. It's kept in memory only and is never written to disk; it's forgotten when the app closes. To try the app without an account, click sample data.
  2. Choose the data. Pick a project, a keyword group, a search engine, the ranking update (date) and the date to compare with. Then click Load.
  3. Set up the plan. Choose your website (the project's main website is preselected), how many keywords to plan (top N by priority), and the search algorithm.
TabWhat you see
KeywordsEvery keyword with its position, its change, and the labels the rules derived for it.
PlanThe plan as quests (one card per keyword), a timeline, or a list. Each step has a checkbox and a “Why this step?” explanation.
QueryAsk questions in plain-English chips or in logic, and read a proof for each answer.
RulesAll rules, grouped in layers (strata), each with a one-line explanation.

3. Where the data comes from

The app calls the AWR API v3 directly from your computer. Only the selected keyword group is downloaded:

  • Projects, ranking dates, keyword groups, search engines and websites come from AWR's project and Market Share endpoints.
  • Positions come from domain-keywords: one small request per website per date, run 8 at a time.
  • Choosing Full ranking export downloads the whole ranking update instead. This is slower.

Caching. Rankings for past dates don't change, so they are saved on disk and loaded instantly the next time. Today's date is always downloaded again. Tick Re-download from AWR to skip the cache.

Privacy. The app only listens on 127.0.0.1, so only your own computer can open it. Every request must carry a per-run secret, and the API key is only ever sent to api.advancedwebranking.com.

4. Why these methods

🎓 School project

This is a project for the Knowledge Representation and Problem-Solving course. The techniques are the ones that course teaches, applied to a real problem: first-order logic, unification, inference with rules, negation as failure, STRIPS planning, and BFS, uniform-cost and A* search. They were chosen to demonstrate the course material, not because they are the only way to build an SEO tool.

A commercial SEO tool would probably hard-code these checks in ordinary if statements. Keeping the knowledge separate from the program, as logic, has advantages that suit both the course and the problem:

  • Declarative: the SEO knowledge lives in a text file (knowledge_base/seo_rules.fol). You can change a rule without touching the code.
  • Explainable: because every conclusion comes from rules applied to facts, the app can show why it concluded something.
  • Queryable: the same knowledge answers questions nobody programmed in advance.
  • Optimal plans: search guarantees the cheapest plan under the stated action costs, instead of a hand-written fixed order.

5. Knowledge representation

Facts

Ranking data is translated into ground facts: statements with no variables. Position 101 means “not found in the top 100”.

FactMeaning
Tracked(K)keyword K is tracked in the AWR project
Ranking(K, P)our position for K on the chosen date
PreviousRanking(K, P)our position on the compare date
CompetitorRanking(K, C, P)competitor website C's position for K
RankingUrl(K, U)our page U that ranks for K (when AWR provides it)
InGroup(K, G)K belongs to the AWR keyword group G

Rules

A rule Head :- Body. reads “the head is true for every choice of variables that makes the whole body true”. In logic: ∀K, P ( Ranking(K, P) ∧ P ≤ 10 → FirstPage(K) ). Words starting with a capital letter are variables.

%% A keyword dropped if it fell 5 or more positions since the previous update.
Dropped(K) :- Ranking(K, P), PreviousRanking(K, P0), D is P - P0, D >= 5.

%% A keyword close to the top that a competitor is beating needs work.
NeedsOptimization(K) :- StrikingDistance(K), LosingToCompetitor(K).

%% Urgent keywords get priority 1.
Priority(K, 1) :- Urgent(K).

The 33 rules are grouped by purpose:

  • Classification: InTop3, FirstPage, StrikingDistance (#4–#20), NotRanking (below #50), Dropped and Improving (±5 positions), BeatenBy, LosingToCompetitor, RankingPageExists.
  • Needs work: off page 1, or dropped, or in striking distance while a competitor is ahead. Everything else is Healthy.
  • Priority: 1 = dropped, 2 = quick win in striking distance, 3 = everything else. Equal priorities are ordered alphabetically.
  • Planning state: Improved, DropHandled, GapHandled, Addressed and Blocked. These depend on the work already done in the plan.

Each rule has a plain-English line (starting with %%), which the Rules tab shows next to it.

“not” and strata

not X uses negation as failure under the closed-world assumption: if X can't be proven from the data, it's treated as false. For example:

Healthy(K) :- Tracked(K), not NeedsOptimization(K).

This is only safe once every NeedsOptimization fact has been derived. Otherwise a keyword could be called healthy too early. The engine therefore sorts the rules into strata (layers). A rule that uses not X is placed in a higher layer than every rule that concludes X. The layers run from bottom to top, each one until nothing new appears. A rule set with a cycle through not is rejected when it's loaded.

6. Queries and proofs

🎓 KRPS context

The Query tab is where the knowledge representation half of the course is most visible. You ask the knowledge base a question in first-order logic, it answers with every variable binding that makes the question true, and it shows the derivation (proof) behind each answer. Unification, forward chaining and negation as failure exist in this project because they are the inference methods the course covers. They are the standard way to answer logic queries over a set of facts and Horn rules.

Query syntax

You writeMeaning
NeedsOptimization(K)Which keywords K need work? A capitalised word is a variable to fill in.
A(K), B(K)A comma means and: both must hold for the same K.
not Dropped(K)K can't be shown to have dropped (negation as failure).
Ranking(K, P), P < 4Comparisons: < > <= >= = !=
D is P - P0Calculation: + - *; the result is bound to D.
Priority('banana bread', P)Constants with spaces go in quotes.
CompetitorRanking(K, _C, P)A variable starting with _ is matched but not shown in the answer.

Examples (the same questions as the chips in the Query tab):

NeedsOptimization(K), BeatenBy(K, C)            % which keywords need work, and who beats us on them?
Dropped(K), Ranking(K, P), PreviousRanking(K, P0), D is P - P0   % how far did each keyword drop?
StrikingDistance(K), not LosingToCompetitor(K)  % quick wins with nobody ahead
InGroup(K, G), Priority(K, 1)                   % urgent keywords and their groups

How a query is answered

  1. Forward chaining. All rules are applied to the AWR facts, stratum by stratum, until a fixpoint. The result contains every fact the rules can derive (the closure).
  2. Conjunctive matching. The conditions in the query are solved left to right. Each condition is unified with the facts, and every successful match extends the substitution (for example {K ↦ 'trail running shoes', C ↦ 'runfast.example'}).
  3. Built-ins and “not”. Comparisons and is are evaluated once their variables are bound. not X succeeds when X has no match in the closure.
  4. Each complete substitution is one answer. It's shown as a sentence and as a table row.

Unification is Robinson's algorithm with the occurs check. It finds the most general substitution that makes two terms equal, e.g. Ranking(K, 14) and Ranking('shoes', P) unify with {K ↦ 'shoes', P ↦ 14}.

Proof trees

During forward chaining, the engine records which rule and which body facts produced each derived fact. For an answer, the Query tab unfolds this into a tree:

“trail running shoes” has priority 1           [rule: Urgent keywords get priority 1.]
└─ “trail running shoes” is urgent             [rule: A keyword is urgent if it needs work because it dropped.]
   ├─ “trail running shoes” needs work         [rule: Anything outside page 1 (below #10) needs work.]
   │  ├─ we rank #14 for “trail running shoes”     [AWR data]
   │  └─ 14 > 10                                   [calculation]
   └─ “trail running shoes” dropped 5 or more positions
      ├─ we rank #14 …, we ranked #5 … in the previous update   [AWR data]
      ├─ 9 = 14 − 5                                              [calculation]
      └─ 9 ≥ 5                                                    [calculation]

Leaves are either AWR data, a calculation, or a “not” check (nothing in the data proves the opposite). Turn on Show the logic too to see the formal notation next to each line.

7. Planning

The planner is a STRIPS-style model:

  • State: the set of work already done (e.g. Audited(K), ContentImproved(K)). The initial state is empty.
  • Actions: each has a precondition written as a logic query, add/delete effects, and a cost (effort points). An action is applicable for every keyword whose precondition the knowledge base can prove, using the same unification and rules as the Query tab.
  • Goal: every keyword in scope has a ranking re-check scheduled: ∀K (InScope(K) → Rechecked(K)). A re-check is only possible once the keyword is Addressed.

Audit pagein scope, not audited, not blockedAudited1

Addressed means: the page is improved (on-page, content or a new landing page), internal links were added, and, where relevant, the drop was investigated and the competitor gap was closed (competitors analysed and content improved).

Strict priority (on by default) adds not Blocked(K) to Audit page. A keyword can't be started while a more urgent keyword in the plan isn't addressed yet. This mirrors how SEO teams work and also makes the search space much smaller.

Effects record work done, never new positions. Whether rankings actually improve is measured by the next AWR update. That's why every plan ends with a re-check.

8. Search: BFS, UCS, A*

Planning is solved as a search through states. From each state, the successors are the states reached by applicable actions. Three algorithms are available:

AlgorithmHow it worksGuarantee
BFSExpands states level by level (fewest actions first). The goal is tested when a state is generated.Shortest plan in number of steps, not the cheapest
UCSAlways expands the state with the lowest cost so far, g(n).Cheapest plan
A*Expands the lowest g(n) + h(n), where h estimates the remaining cost. Ties go to deeper states.Cheapest plan, because h is admissible

The heuristic. For every keyword that isn't finished yet, h adds the cost of the cheapest action for each step the rules make unavoidable. Examples: 1 for the re-check, 1 for links, 1 for the audit, 2 to investigate a drop, 2 + 4 to analyse competitors and close the gap, and 8 for a landing page when we don't rank. Each step is counted at its cheapest possible price and only when it's truly required, so h never overestimates. It is admissible, so A* still returns an optimal plan. There's also a simpler goal-count heuristic (the number of keywords not yet re-checked), useful for comparison.

Results on the sample data (3 keywords, strict priority):

AlgorithmStepsCostStates expanded
BFS1437264
UCS1731277
A*173117

BFS finds a plan with fewer steps, but it costs more. UCS and A* both find the cheapest plan, and A* expands about 94% fewer states. Choose Compare all three as the algorithm in the app to run all three on your own data.

9. Limitations

  • Action costs are fixed estimates of effort, not measured hours.
  • The planner doesn't predict ranking changes. It plans work, and the next AWR update shows the effect.
  • When a single group is loaded, keywords where none of the tracked websites rank don't appear, because AWR's domain-keywords endpoint doesn't list them.
  • The planner works best on the top 3–8 most urgent keywords at a time. Larger plans grow the search space quickly, especially without strict priority.

10. Glossary

Fact
A true statement with no variables, e.g. Ranking('shoes', 14).
Rule
“If the body holds, the head holds”, for every value of its variables.
Variable
A capitalised name (K, P) that stands for any value.
Substitution
An assignment of values to variables, e.g. {K ↦ 'shoes'}.
Unification
Finding a substitution that makes two expressions identical.
Forward chaining
Repeatedly applying rules to known facts until nothing new can be derived.
Closed-world assumption
Anything not known to be true is assumed false.
Negation as failure
not X succeeds when X can't be proven.
Stratum
A layer of rules. Lower layers are finished before higher layers use not on their conclusions.
STRIPS
A way to describe actions by preconditions, facts added and facts deleted.
Admissible heuristic
An estimate of the remaining cost that never overestimates it, which keeps A* optimal.
Striking distance
SEO term for positions #4–#20, where a little work can bring a keyword to the top.
